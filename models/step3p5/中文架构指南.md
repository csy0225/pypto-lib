## 1. 写在最前面：什么是 step3p5

step3p5 是一个 LLM,本目录是它在 **昇腾 NPU**(Ascend 910B/C)上的实现,
跑在 **8 张卡同节点** 部署里。三个不变量先记住:

- **TP_WORLD_SIZE = 8** —— Tensor Parallelism,把矩阵权重沿头/中间维切 8 份。
- **EP_WORLD_SIZE = 8** —— Expert Parallelism,把 288 个 MoE 专家切成
  8 份每张卡 36 个。
- **world_size = 8** —— TP 组与 EP 组同居一个 8 卡 world,**每张卡一个进程**。

模型结构上要记住的:
- 共 45 个主层 + 3 个 MTP 层。
- 主层中 attention 有两种:**full**(64 头)和 **swa**(96 头, 滑窗 512)。
- 主层中 MLP 有两种:layer 0..2 是 **dense**,layer 3..44 是 **MoE**(top-8/288)。
- 因此每层程序的"基因"由两位决定:`{full, swa}` × `{dense, moe}`,
  共 8 种特化 —— 这是 `decode_layer.py` 名字这么多的原因。

## 2. SPMD 心智模型:单程序、多份数据

**SPMD = Single Program, Multiple Data**。

理解 SPMD 最简单的口诀: **同一份代码,在很多张卡上同时跑;每张卡只看到自己那一份数据**。
谁要和邻居交换数据,就显式调用一次"集合通信"原语(collective)。

step3p5 里 SPMD 在 **三个尺度** 同时存在,容易混,先讲清楚:

| 尺度 | 单位 | 程序员手里的接口 | 谁来分发 |
|------|------|------------------|----------|
| **跨卡(节点级)** | 8 张 NPU | `pld.tile.remote_load` / `pld.tensor.put` / `pld.system.notify`(在 collectives.py 里被封装为 `tp_all_reduce` 等) | host_orch 启动 8 个进程,每个进程对应 1 张卡;每张卡内的 kernel 用 `pld.world_size()` / `pld.my_rank()` 知道自己是谁 |
| **跨核(片上)** | 1 张卡里的多个 AICore/AIV | `pl.spmd(N, name_hint=...)`、`pl.parallel(...)` | pypto 编译器(把 spmd body 自动 outline 成多核函数),由 chip_orch 在卡上分派 |
| **单核内流水** | 同一个核上的 cube / vector / mte 三个流水线 | `pl.pipeline(stage=N)` + 算子并存在同一个 `pl.at` 区里 | 编译器调度 |

> 当你看到 `for i in pl.spmd(N):`,**这是片上多核的 SPMD,不是跨卡的**。
> 跨卡的"我是哪一张卡"靠 `pld.my_rank()` 拿,跨卡通信只能用 `pld.*` 命名空间。
>
> 这一点是新手最容易混淆的:`pl.spmd` 和"分布式"没有任何关系,`pld` 才是分布式。

## 3. pypto 三层执行体:host_orch / chip_orch / InCore

step3p5 几乎每一个 `@pl.program` 类内都长这样三层:

```
┌─────────────────────────────────────────────────┐
│ host_orch  ← 跑在 host CPU 的 Python              │  level=HOST, role=Orchestrator
│   • 启 8 个进程对应 8 张卡                        │
│   • 用 pld.alloc_window_buffer(...) 分配跨卡 scratch│
│   • 把 buffer 切成 pld.window(...) 喂给 chip_orch  │
└─────────────────────────────────────────────────┘
                  │
                  ▼ (per-rank chip launch)
┌─────────────────────────────────────────────────┐
│ chip_orch  ← 跑在 AICPU(每张卡的控制核)         │  type=Orchestration
│   • Python 风格的串行 / parallel 循环             │
│   • 调用本类的 InCore 方法把 tile 推给 AICore      │
│   • 调用 self.tp_all_reduce(...) 等 collective    │
└─────────────────────────────────────────────────┘
                  │
                  ▼ (per-tile launch)
┌─────────────────────────────────────────────────┐
│ InCore body ← 跑在 AICore/AIV(向量+矩阵单元)    │  type=InCore  或  pl.at(level=CORE_GROUP)
│   • 真正写 vec/cube/mte 算子的地方                │
│   • pl.spmd / pl.pipeline / pl.range 在这一层     │
│   • 任何 pld.* 调用必须在这一层以下                │
└─────────────────────────────────────────────────┘
```

### 一个要记的对应关系

| pypto 概念 | 物理对应 | step3p5 文件里典型形式 |
|------------|----------|----------------------|
| `host_orch` | host CPU 启动器 | `@pl.function(level=pl.Level.HOST, role=pl.Role.Orchestrator)` |
| `chip_orch` | AICPU 控制核 | `@pl.function(type=pl.FunctionType.Orchestration)` |
| InCore body | AICore + AIV | `@pl.function(type=pl.FunctionType.InCore)` 或 `@pl.function(type=pl.FunctionType.Opaque)` 内的 `with pl.at(...)` 块 |

> **看到 `host_orch` 出现 `pld.alloc_window_buffer(...)` 不要慌**:
> 这是给跨卡通信用的 scratch + signal cells,**只能在 host_orch 分配,而不能在 chip_orch 里分配**。

## 4. 装饰器全景

### 4.1 Form A: `@pl.jit` + `@pl.jit.inline`

**模块级函数风格**,步骤简单(没有类),每个 helper 各自是一个普通 `def`,
用装饰器告诉 pypto"这是个可被 inline 的小 kernel"或"这是个独立 kernel 入口"。

| 装饰器 | 角色 |
|--------|------|
| `@pl.jit` | 顶层 entry,golden test 调用的边界,有 `pl.Out[...]` 形参作为输出 |
| `@pl.jit.inline` | 可被 inline 的子 kernel;**必须有返回值**(parser 要求每个 inline call 是表达式) |

**典型例子**(`_ops.py`):

```python
@pl.jit.inline
def zero_centered_rmsnorm_apply(normed_fp32, gamma_slice):
    gamma_eff = pl.adds(gamma_slice, 1.0)
    return pl.col_expand_mul(normed_fp32, gamma_eff)
```

step3p5 里 Form A 主要用在三个地方:
- `_ops.py`:RMSNorm / RoPE / 头门控等 helper。
- `collectives.py`:`tp_all_reduce` 等 4 个集合通信封装。
- 各 attention/MoE 文件中"InCore 之前预先组装好的"小工具。

### 4.2 Form B: `@pl.program` + `@pl.function`

**类风格**,把一组相关 kernel 当作 class 的方法绑在一起。step3p5 里**绝大多数完整 kernel 走 Form B**,因为:

1. host_orch / chip_orch / InCore 三层都在同一个 class 里,共享 `self.*`,代码组织清晰。
2. `self.tp_all_reduce(...)` 这种"被吊起为方法"的集合通信原语,只在 Form B 才能调用(见 §4.5)。
3. 一个类一份 program,直接给 `pypto.ir.compile(MyProgram, ...)` 就能产出多卡可执行包。

**典型骨架**(摘自 `decode_layer.py`):

```python
@pl.program
class DecodeLayerDense:
    @pl.function(type=pl.FunctionType.InCore)
    def _attention_full_body(self, ...):  # 跑在 AICore
        ...

    @pl.function(type=pl.FunctionType.Orchestration)
    def chip_orch(self, ...):              # 跑在 AICPU
        for ... in pl.parallel(...):
            self._attention_full_body(...)
        self.tp_all_reduce(...)            # 集合通信(InCore方法被lift)

    @pl.function(level=pl.Level.HOST, role=pl.Role.Orchestrator)
    def host_orch(self, ...):              # 跑在 host CPU
        scratch = pld.alloc_window_buffer(...)
        self.chip_orch(...)
```

### 4.3 `@pl.function(type=…)` 四种类型

| `type=` | 物理位置 | step3p5 用在哪 |
|---------|----------|------------|
| `InCore` | AICore/AIV | 单个 kernel body,真正算 matmul/vec |
| `Orchestration` | AICPU | chip_orch:循环+调度 InCore 方法 |
| `Inline` | 视调用点 | 像 `@pl.jit.inline`,但作为 class 方法存在 |
| `Opaque` | 自包含 kernel | 用 `pl.at` 自划 InCore 边界(step3p5 用得少,见 docs/pypto-coding-style.md §1) |

**InCore vs Inline 的差别**: InCore 编译为一个独立的 kernel 入口,有自己的 launch 开销;Inline 在调用点被 splicing 进去,**没有独立的 launch**,适合"复用同一段代码,避免重复写 = 又不想多花 launch"的场景。`decode_layer.DecodeLayerMoE` 把 EpTpMoE 的所有方法以 Inline 方式拍扁就是这个原因(见 §4.5)。

### 4.4 `@pl.function(level=Level.HOST, role=Role.Orchestrator)`

step3p5 里固定就一句:

```python
@pl.function(level=pl.Level.HOST, role=pl.Role.Orchestrator)
def host_orch(self, ...):
    tmp_window = pld.alloc_window_buffer(...)   # 只能在这里
    self.chip_orch(..., tmp_window=tmp_window)
```

这是 **host CPU** 上的 Python,在跨卡分布式任务里"它先于一切被执行"。
它的责任只有两件:**分配跨卡 windows / signals**、**调一次 chip_orch**。

### 4.5 两种 Form **不能混用**

> ⚠️ **新手最容易踩的坑**

`@pl.jit.inline` 函数 **不能** 从 `@pl.function(type=InCore)` body 里直接调。pypto frontend 的 AST parser 看到这种调用会拒掉。你只能在两种世界里二选一:

| 世界 | 组合方式 | 调用 |
|------|----------|------|
| jit 世界 | `@pl.jit` + `@pl.jit.inline` | inline helper 通过 caller 模块的 globals 被 `InlineFunctions` IR pass splicing 进入 |
| program 世界 | `@pl.program` + `@pl.function` | `self.method(...)` 通过类成员调用 |

**所以 step3p5 的 collective 封装故事是这样的**:

- `collectives.py` 里 `tp_all_reduce` 的"事实实现"是 `@pl.jit.inline`(Form A)。
- 但调用方都是 `@pl.program` 类(Form B),不能直接调 `tp_all_reduce(...)`。
- 解决方案:`@pl.program` 类里再 **复制一份同名方法**(`def tp_all_reduce(self, ...)`),把 `@pl.jit.inline` 体复制进来。这就是为什么你在 `attention_full.py`、`attention_swa.py`、`decode_layer.py`、`moe.py` 都能看到一份"local copy of tp_all_reduce"。

把上面这点记牢,你看代码就不会困惑"为什么同一个东西被复制了 N 遍"。

## 5. `pl.at` 作用域 —— InCore 与 orchestration 的边界

**`pl.at` 是给"自包含 kernel"(Form A 的 `@pl.jit` / Form B 的 `Opaque`)用的**。

```python
with pl.at(level=pl.Level.CORE_GROUP, name_hint="q_proj"):
    # 这一段会被 lower 到 InCore
    for kb in pl.pipeline(K_BLOCKS, stage=2):
        ...
```

要点:
- `level` 在 pypto-lib 里 **只用 `pl.Level.CORE_GROUP` 一种**。
- `name_hint` 强烈建议写,会出现在生成的 kernel 文件名 / profiling trace 里,方便定位单 kernel 的问题。
- 可以嵌套 `pl.at`:外层划 InCore 边界,内层用不同 `name_hint` 再切子 kernel。
- step3p5 里使用 `pl.at` 的地方主要在 attention_full/swa 的 `chip_orch` 内,
  对那些"轻量、不值得开 InCore method"的小段(rmsnorm/rope 写 kv cache)用 `pl.at` 就地下沉。

如果你直接写 `@pl.function(type=pl.FunctionType.InCore)`,**body 里就不要再写 `pl.at`** —— 整个 body 已经默认是 InCore 了。

### 关于 `optimizations=[pl.split(...)]`

`pl.at` 和 `pl.spmd` 都接受 `optimizations=[...]`。最常见的一种 `pl.split(pl.SplitMode.UP_DOWN)` 是把 cube + vector 混合区一分为二让两条流水线交叉跑;只在 cube 和 vector 同时存在的区里有效。step3p5 的 attention_full/swa qk_matmul + softmax 区会用到。

## 6. 四种循环:`pl.range` / `pl.parallel` / `pl.pipeline` / `pl.spmd`

四种循环按 **位置 × 语义** 各占一格:

| 循环 | 在 orch 层(`chip_orch` body 或 `pl.at` 外) | 在 InCore 内 | 含义 |
|------|:---:|:---:|------|
| `pl.range` | ✅ | ✅ | 严格串行,允许循环间依赖 |
| `pl.parallel` | ✅ | ❌ | 迭代 **完全独立**,编译器可任意拆/调度到多核 |
| `pl.pipeline` | ❌ | ✅ | 串行,但相邻迭代被 software-pipelined,常用作 cube 矩乘 K-loop |
| `pl.spmd` | ✅(body 是隐式 InCore) | ❌ | **片上 SPMD**:把 N 个 block 一次性分派给多核;body 自动被 outline 成 InCore 函数 |

### 关键差别一句话

- `pl.parallel(stop)` —— "你随便拆,我保证迭代之间没依赖"。
- `pl.spmd(N)` —— "我希望 N 个块同时起,在 N 个核上跑"。这是 step3p5 里最常出现的(每个 `name_hint="..._proj"` / `..._matmul"` / `..._softmax"` 都是一段独立的 kernel)。
- `pl.pipeline(K, stage=4)` —— "K 个 tile 顺序处理,但每 4 个 stage 错峰让 cube 和 vec 交替忙"。
- `pl.range` —— "我就是普通 Python for"。

### 参数形式

`pl.range / pl.parallel / pl.pipeline` 形参和 Python `range` 一样:`(stop)` / `(start, stop)` / `(start, stop, step)`。`pl.spmd` 只吃 **block 数**(从 0 起步,步长 1),关键字 `name_hint=` 强烈建议给。

## 7. 数据搬运三件套:`pl.create_tensor` / `pl.slice` / `pl.assemble`

```python
# 1) 在 orchestration 层(pl.at 之外)分配中间张量
q_proj = pl.create_tensor([batch_padded, q_hidden], dtype=pl.BF16)

for q0 in pl.parallel(0, q_hidden, Q_OUT_STEP):
    q_acc = pl.create_tensor([BATCH_TILE, Q_OUT_STEP], dtype=pl.FP32)
    with pl.at(level=pl.Level.CORE_GROUP, name_hint="q_proj"):
        # 2) slice: 从 GM 加载子区域(自动 lower 为 TLOAD)
        tile_a = pl.slice(normed_tile, [BATCH_TILE, K_STEP], [0, k0])
        tile_b = pl.slice(wq, [K_STEP, Q_OUT_STEP], [k0, q0])
        q_acc = pl.matmul(tile_a, tile_b)
        q_bf16 = pl.cast(q_acc, target_type=pl.BF16)
        # 3) assemble: 把 tile 写回 GM(自动 lower 为 TSTORE)
        q_proj = pl.assemble(q_proj, q_bf16, [b0, q0])
```

要点:
- **`pl.create_tensor` 只能在 orchestration 层用**,InCore 区里不能用。
- `pl.slice(tensor, sizes, offsets)` 注意 **顺序是 (sizes, offsets)**,不是 (offsets, sizes)。
- 短写法 `tensor[a:b, c:d]` 等价于 `pl.slice`;赋值 `tensor[a:b, c:d] = tile` 等价于 `pl.assemble`。
- `valid_shape=[h, w]` 标记动态有效形状(如 batch 不满整 tile),compiler 会自动 0 填充尾部。

## 8. Vector / Cube / MTE 三类硬件单元

只用一句话+一个例子:

| 类别 | 跑在哪 | 干什么 | 例子 |
|------|--------|--------|------|
| **Vector(AIV)** | 向量单元 | 逐元素算子、reduce、广播、cast、softmax 的 epilogue | `pl.add` `pl.mul` `pl.row_sum` `pl.row_expand_mul` `pl.cast` |
| **Cube(AIC)** | 矩阵单元 | matmul 一族 | `pl.matmul` `pl.matmul_acc` `pl.matmul_bias` `pl.gemv` |
| **MTE** | DMA + view | 数据搬运、视图 reshape | `pl.create_tensor` `pl.slice` `pl.assemble` `pl.reshape` |

> 一个 `pl.at` 区里可以同时混 Vec + Cube 算子,编译器会自动把它们排到合适的流水线上,这是 step3p5 attention 里"matmul + cast + assemble" pattern 的依据。

## 9. 分布式:TP=8 + EP=8 拓扑、`pld` 与四个 collective

### 拓扑

- 单节点 8 张昇腾卡;每张卡一个 Python 进程。
- TP 组与 EP 组 **同居** 一个 `world_size = 8` 的 world。
- 通信永远是 **全员参与的** —— 4 个原语对应 4 种典型流量:

| 原语 | 大致语义 | step3p5 用在哪 |
|------|---------|----------------|
| `tp_all_reduce` | TP 组内 sum,每张卡输入输出同 shape;典型实现 = ring reduce-scatter + ring all-gather | attention 的 o_proj 之后、dense MLP 的 w_down 之后、MoE 共享专家之后、MTP eh_proj 之后 |
| `tp_all_gather` | TP 组内沿某轴拼起来 | LM head logits 路径里(目前没启用,设计上可选) |
| `tp_reduce_scatter` | TP 组内 sum 然后切给每张卡 | (内部用,见 collectives.py) |
| `ep_all_to_all` | EP 组每张卡互相分发 token | MoE 的 dispatch.py(发送)和 combine.py(回收) |

实现细节都在 `collectives.py` 里,基于以下 pypto.distributed 原语:

| `pld` 命名空间 | 作用 |
|----------------|------|
| `pld.tile.remote_load(target, peer, offsets, shape)` | 从 peer 卡 **拉** 一个 tile(pull-side ring 用这个) |
| `pld.tensor.put(dst, peer=, src=, atomic=)` | 往 peer 卡 **推** 一整个 tensor;支持 AtomicAdd |
| `pld.system.notify(target, peer, offsets, value, op)` | 给 peer 写一个信号格,典型 op = `AtomicAdd` 或 `Set` |
| `pld.system.wait(signal, offsets, expected, cmp)` | 自旋等信号格达到阈值(`Ge`) |
| `pld.window(buf, shape, dtype=…)` | 把 host_orch 分配的字节 buffer 视图化为强类型 DistributedTensor |
| `pld.alloc_window_buffer(n_bytes)` | **host_orch 专用**:分配跨卡 scratch slot |

### 双 buffer 协议(scratch + signal)

每一次 collective 都需要 host_orch 配一对儿 buffer:

| buffer | shape | 作用 |
|--------|-------|------|
| `tmp_window` | 通常 `[BATCH, HIDDEN // TP_WORLD_SIZE]` BF16 | 拉链/推链中转区 |
| `signal_window` | `[group_size, 1]` INT32 | 每个 ring step 由 `AtomicAdd` 加 1,接收方 `wait(>=expected)` |

**坑**:signal_window 的 cells 是 AtomicAdd 累加的,跨 collective **不能复用同一个 slot**(否则下一次的阈值会错乱)。所以 step3p5 的 `decode_fwd.py` 给每个 attention/MLP/MoE call site 都单独 alloc 一个 signal_window。

## 10. step3p5 调用链:从 `step3p5_decode.py` 到一个 kernel

```
step3p5_decode.py                # CLI 入口、torch reference smoke、host 真机入口
   └── decode_fwd.Step3p5DecodeFwd        @pl.program
        ├── host_orch  (alloc 所有跨层共用的 window pool)
        └── chip_orch  (Python for 循环 45 层)
             └── select_decode_layer(idx)                        ← decode_layer.py
                  ├── DecodeLayerDense (idx 0..2)        @pl.program
                  │    ├── host_orch  (alloc 本层 window)
                  │    ├── chip_orch  (调 attention + dense MLP)
                  │    │    ├── pl.inline(attention_full / attention_swa)
                  │    │    └── _dense_mlp_body_tp + self.tp_all_reduce(...)
                  │    └── @pl.function(InCore)  各 kernel body
                  └── DecodeLayerMoE (idx 3..44)         @pl.program
                       ├── host_orch
                       ├── chip_orch
                       │    ├── pl.inline(attention_full / attention_swa)
                       │    └── inlined EpTpMoE body(gate→dispatch→routed→shared→combine)
                       └── @pl.function(Inline) 一堆原 EpTpMoE 方法被拍扁过来
        └── 最后一层之后:
             rms_lm_head.RmsLmHead.chip_orch   (vocab 切片 LM head matmul)
```

### 为什么 EpTpMoE 在 DecodeLayerMoE 里被"拍扁"

pypto frontend 不允许在一个 `@pl.program` body 里实例化另一个 `@pl.program`。所以 `decode_layer.DecodeLayerMoE` 不能 `embedded = EpTpMoE(...)` 然后 `embedded.chip_orch(...)`。变通做法是把 `moe.EpTpMoE` 的每一个 `@pl.function` 方法 **逐字复制** 到 `DecodeLayerMoE`,改成 `@pl.function(type=pl.FunctionType.Inline)`(避免每个方法各自起一个独立 launch)。原 `EpTpMoE` 仍单独保留,用于 `_compile_moe.py` codegen 验证(单跑 MoE 块)。

prefill 侧 `prefill_moe.py` 的 `PrefillMoE` 同样把 EpTpMoE 拍扁了一份,但又额外做了一件事:把 `T_prefill` 切成 `BATCH=16` 的 tile 循环,因为 EpTpMoE 内部 `T = BATCH = 16` 是 hard-coded 的。

## 11. 推荐阅读路径

如果你只有 30 分钟:
1. `_smoke_program_build.py`(70 行,看 program build 的最小入口)。
2. `_ops.py`(看 `@pl.jit.inline` 长什么样、helper 怎么写)。
3. `collectives.py` 头部 docstring(看 `tp_all_reduce` 的双 buffer 协议)。
4. `decode_layer.py` 找 `DecodeLayerDense` 类,扫一遍 host_orch / chip_orch / 一个 InCore 方法。
5. `decode_fwd.py` 看 45 层是怎么循环起来的。

如果你要深挖一类问题:
- **想看 attention** → `attention_full.py`(64 头 → 8/卡)或 `attention_swa.py`(96 头 → 12/卡 + 滑窗)。
- **想看 MoE** → `gate.py` → `dispatch.py` → `expert_routed.py` / `expert_shared.py` → `combine.py` → `moe.py` 串起来。
- **想看 prefill** → `prefill_qkv_proj_rope.py` → `prefill_attention_full.py` / `prefill_attention_swa.py` → `prefill_moe.py` → `prefill_fwd.py`。
- **想看 host 端权重加载** → `weight_loader.py`。
- **想看真机入口** → `step3p5_decode.py` / `step3p5_prefill.py`。
- **想看 codegen 验证** → `_compile_*.py`(每个对应一个 phase)。
